# 寻路实验台（完全隔离）

不启动游戏，直接喂真实代价网格，跑**游戏里那份** `RwxAStar.java`（原样拷入，不改）。
目录：`tools/pathlab/`

## 怎么跑

```bash
# 批量：300 组随机起终点，出统计
bash tools/pathlab/run.sh

# 单例：起点 40,180 -> 终点 200,60
bash tools/pathlab/run.sh 40 180 200 60
```

输出：`tools/pathlab/out/worst.ppm`（最差偏离案例）、`out/path.ppm`（单例）。
灰度 = 可走格，深色 = 不可走，红 = 路径，绿 = 起点，蓝 = 终点。

## 数据

`data/cost-LAND.csv`：从运行中的游戏导出的陆军代价图，Crossing Large (10p)，230×230。
-2 = 不可走，其余 = 该格代价。来源 `docs/images/rwx-grid-cost-LAND.csv`。

## 首次实测（2026-11-23）

```
cases=300 ok=226 fail_unreachable=63 fail_astar=11
avgNodes=111 borderHitsTotal=56 pairsEndNearBorder=34
worstDeviation=72.5 case=183,208 -> 205,38
```

结论：
1. **A* 不贴边界**。226 条成功路径里共 56 个贴边航点，全部来自「起终点本身就在边界附近」的 34 组。
   内点之间的路径贴边数为 0。
2. **11/300 在可达情况下 A* 放弃**（MAX_EXPAND=6000 太小），这是真 bug。
3. **最差偏离 72.5 格是地形导致的合理绕行**（两端被大片水域隔开），不是算法走歪。
   → 说明「偏离起点-终点连线超过 3 格就删航点」这条规则会误删正确路径点。
4. 平均 111 个航点 = 逐格一个点，和引擎原路径一致。

## 边界

- 只测了陆军（LAND）代价图，海军/悬浮/飞行没测。
- 代价全部为 0（这张图没有代价>0 的地形），所以 COST_SCALE 加权效果测不出来。
- 实验台不含 `PathSolver.e()/g()` 的扫描逻辑，只测 A* 本体。

| HOVER | 0 | 1 | 3 | 0 | 0 | 走不了 | 走不了 |

| 地图 / 类型 | 有效组数 | 成功 | 平均代价 | 代价盲选基线 |
| --- | --- | --- | --- | --- |
| roads / LAND | 100 | 100 | 47 | 166 |

| swampfield / LAND | 100 | 100 | 21 | 316 |
| swampfield / HOVER | 100 | 100 | 16 | 157 |
| river / LAND | 100 | 100 | 42 | 89 |

| river / HOVER | 100 | 100 | 17 | 42 |

| lava / HOVER | 100 | 100 | 136 | 176 |

结论：
1. 六张图 × 三种移动类型，`fail_astar` 全部为 **0**（上限 60000 之后）。

## 第四轮：把 g() 拉进来 —— 结论是它是死代码

`PathSolver.b()` 的分发逻辑：

```java
if (this.D instanceof DynamicUnitPath) { f(); ... }   // f() 就是 g()
else { linkedListE = rwxUseSolver2() ? RwxPathSolver2.solve(...) : e(); }
```

而 `DynamicUnitPath` 只在 `PathEngine.a(boolean)` 里、且 `OrderableUnit.L` 为 true 时才会创建：

```java
if (OrderableUnit.L) { path = new DynamicUnitPath(this, z); } else { path = new Path(this, z); }
```

`OrderableUnit.L` 的声明是 `public static boolean L = false;`，**全仓库没有任何一处把它改成 true**。
→ `DynamicUnitPath` 永远不创建 → `g()` 永远不执行。

运行期证据（干净环境重跑，4000 tick，42 台单位，600 条移动指令被接受，单位平均移动 135 世界单位）：

| 计数项 | 数值 |
| --- | --- |
| RWX_SOLVER e（普通求解器） | 20（日志上限） |
| RWX_SOLVER g（逐帧动态重算） | **0** |
| RWX_PATHTRACE（可疑路径） | **0** |
| RWX_REPATH_MOVE（移动中改路） | **0** |
| RWX_REFINE（试算评估触发重算） | 6 |
| RWX_PRUNE_SAFE（求解器剪枝） | 14 |
| logs/rwx-scan.csv | 未生成 |

结论：
1. `g()` 是死代码，我之前担心的「逐帧重算造成边界航点」不成立。
2. 这场真实对战里，**没有任何一条路径出现贴边航点、末点不等于目标、或判不可达**（PATHTRACE=0）。
3. 剩下的嫌疑只有两个：`requestPathToTarget` 的直线捷径（已加逐格校验）和命令坐标钳制。

## 怎么复现这一轮

```bash
cd /d/Game/RWX-整合包
rm -f logs/rwx-prof.log logs/rwx-scan.csv
runtime/bin/java.exe --enable-native-access=ALL-UNNAMED --sun-misc-unsafe-memory-access=allow \
  -Dfile.encoding=UTF-8 -Dbench.pace=false -Dbench.target=40 -Dbench.batch=20 -Dbench.interval=4 \
  -Dbench.spread=8 -Dbench.agent=1 -Dbench.agentMax=12 -Dbench.agentMoveTick=80 \
  -jar RWX-windows-x64-1.1.4.jar --render-backend=headless \
  --map="maps/skirmish/[p2]Beach landing (2p) [by hxyy].tmx" --ticks=4000
```

注意：`--map` 不能带 `assets/` 前缀（引擎自己会拼 `assets/`，带前缀会变成 `assets/assets/...` 然后加载失败）。

## 第五轮：直线捷径 与 命令钳制 分开测（headless 对战）

### A. 直线捷径（正常目标，3000 tick，504 条移动指令被接受）

| 计数项 | 数值 |
| --- | --- |
| RWX_STRAIGHT taken（捷径通过逐格校验被采用） | 8 |
| RWX_STRAIGHT rejected（粗判通过但逐格校验否掉） | 7 |
| RWX_STRAIGHT illegal（捷径产出的航点落在不可走格） | **0** |
| RWX_PATHTRACE（贴边/末点跑偏/不可达） | 0 |
| RWX_REFINE（试算评估触发重算） | 267 |
| RWX_PRUNE_SAFE | 627 |
| 单位平均移动 | 80.8 世界单位 |

15 次捷径尝试里 7 次被逐格校验否掉（47%）。这 7 次如果没有校验，就会按直线硬走——**这就是“单位不认地形”的直接来源**。
被采用的那 8 次，产出的航点逐点核对，落在不可走格上的数量是 0。

### B. 命令钳制（目标故意丢到 -2500 / 9000，3000 tick，600 条指令被接受）

| 计数项 | 数值 |
| --- | --- |
| RWX_CLAMP_REJECT（越界命令被丢弃） | 12（日志上限） |
| RWX_SOLVER e（求解器被调用） | **0** |
| RWX_STRAIGHT taken | 4 |
| RWX_STRAIGHT illegal | 0 |
| RWX_PATHTRACE | 0 |
| RWX_REFINE | 0 |
| 单位平均移动 | **0.3** 世界单位 |

越界命令全部在进入寻路前被丢掉，求解器一次没被调用，单位基本没动（0.3）。
说明「坐标钳制把路径挪到边界」这条路在入队阶段就被堵住了。

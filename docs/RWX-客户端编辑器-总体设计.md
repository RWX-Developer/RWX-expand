# RWX 客户端编辑器（IDE）总体设计稿

状态：设计稿，未开工。本文件是施工图，不代表任何能力已实现。

## 0. 一句话

把「改游戏的一切」从「手改 ini + 记事本 + 反复重启」变成一个带校验、能预览、能打包的桌面 IDE。
三种模式共用一套底座，只是编辑对象和产物不同。

## 1. 两种模式，两种产物（v2，按老师口径）

| 模式 | 目标（改什么） | 产物 | 谁用 |
| --- | --- | --- | --- |
| 模组编辑器 Mod Editor | **平台契约**：官方 RWX 的 mod-api + ini 规范 | 一个模组（jar：ini + Kotlin + assets） | 只想做模组的开发者 |
| 客户端编辑器 Client Editor | **引擎源码树**：UI、接口设计、模式设计、玩法 | 一个全新客户端（软件 / 整合包） | 需要改游戏本体的开发者 |

打包不是第三种模式，是**客户端编辑器的导出阶段**：把改过的引擎 + 选定模组合成一份可分发的软件。
模组编辑器的导出就是打包一个 mod jar，不需要构建整个客户端。

## 2. 现有可复用资产（已勘）

- UI：Compose Desktop 已接入（desktop 模块 42 个 kt，Compose + Skia/Slick 双渲染后端，已有 SwingAppHost）。
- 数据：`ModManager.loadJvmMods()` 扫描 mods；`IniFile` 解析器；`TileMap`；`UnitStatisticsManager`。
- 校验：rw-modding-mcp 的 lint（18 事件 / 27 逻辑函数 / 键表）已在仓库外可用，可作为校验规则来源。
- 台架：bench-mod（无头跑、可注入单位/触发条件）可当「局内预览」的驱动。

**关键限制：`IniFile` 只解析不写回**（解析时跳过 `#` 注释，只有 LinkedHashMap 值与 setValue，无序列化）。
所以模组编辑不能用 IniFile 存盘，必须另做无损文档模型。

## 3. 统一底座（三模式共用）

1. **Workspace**：工程根、最近打开、模式切换、任务队列。
2. **Document**：以文本为真源（行数组，保留注释/顺序/空行），旁边挂语义 AST 索引（section→key→value 位置）。
   所有编辑操作走「改动文本 → 重算受影响 AST 片段」，保证存盘字节只差用户改的那部分。
3. **事务/撤销**：命令栈（插入/替换/删除文本区间），粗粒度即可，先不做 CRDT。
4. **校验器**：可插拔 lint 管道，输出 文件/行号/级别/说明，点一下跳到问题处。
5. **预览器**：局外预览（资源缩略图、图标、贴图集）＋ 局内预览（起 headless/嵌入 Slick 一局，注入单位或改后的模组）。
6. **任务队列**：校验、构建、打包、局内预览都是后台任务，带进度与取消。
7. **诊断面板**：日志、错误、变更摘要。

## 4. 能力矩阵

| 能力 | Packaging | Client | Mod |
| --- | --- | --- | --- |
| 工作区/任务队列 | ✓ | ✓ | ✓ |
| 无损文档模型 | 清单/脚本 | toml | ini / mod-info |
| 校验器 | 清单完整性 | 键名与取值 | ini 语义 + 逻辑表达式 |
| 局内预览 | 无 | 生效预览 | ✓（核心） |
| 构建产物 | ✓（核心） | 导出配置 | 导出 .rwmod |

## 5. 第一阶段最小切片（P0，先走通一条线）

模组编辑模式里：**打开 mods/units 下某模组 → 单位列表 → 选中单位 → 编辑一个字段 → 校验 → 保存**，
保存后文件字节只差被改的那一行（注释、顺序、空行全保留）。

不含：撤销、局内预览、打包模式。

验收：拿 wcmodoperation 那个模组（1705 条 autoTrigger）当样本，
打开不卡（目标 < 1s 出结构树）、改一个字段存盘后 `lint` 无新增错误、diff 只有目标行。

## 6. 路线

- P0：底座 + 模组模式的只读浏览（结构树 + 文本视图 + 校验面板）。
- P1：字段编辑 + 保存（无损）+ 撤销；表达式编辑器（逻辑布尔高亮/补全）。
- P2：局内预览（headless 快照式）；客户端编辑模式的设置项。
- P3：打包模式（清单、差异、构建、CHANGED-FILES 生成）。

## 7. 与现有代码的衔接点

- `desktop/src/main/kotlin/io/github/rwx/DesktopMain.kt`：应用入口，挂新窗口/模式切换。
- `desktop/.../SwingAppHost.kt`、`ComposeTexturePanel.kt`：Compose 与游戏面板共存的方式，编辑器复用。
- `core/.../mod/ModManager.java`：模组扫描与启用状态；编辑器要读同一份扫描结果。
- `core/.../utility/IniFile.java`：只做语义参考，不用于存盘（会丢注释）。
- `core/.../units/custom/CustomUnitConfigParser.java`：字段语义与默认值的真源，表单据此生成。
- `bench-mod`：局内预览的驱动手段（注入单位/条件）。

## 8. 需要老师定的关键决策

1. 编辑器形态：**独立 Compose 窗口**（推荐，好做多面板/快捷键）还是游戏内覆盖层？
2. 文档真源：**文本为真源 + AST 缓存**（推荐，保注释、diff 干净）还是 AST 为真源再序列化（实现简单、会重排注释）？
3. 打包模式目标：沿用现在的 jpackage app-image + 整合包布局，还是定义新格式（zip + 清单）？
4. 局内预览做到什么程度：headless 截图式（快、不许交互）还是嵌入 Slick 实机跑（能交互、成本高）？
5. 编码：现有 mod ini 的编码需要实测确认（GBK / UTF-8 / 混合），编辑器读写要按实测来，不能猜。

## 9. 风险

- **编码**：中文 mod 名/文本在日志里是乱码，存盘若按错编码会毁文件 → 读写前先探测并保留 BOM/换行风格。
- **解析性能**：大模组 unitParse 在 500～800ms 量级，结构树要增量解析，不能每次全量。
- **热重载**：改完 ini 能否不重启游戏生效，决定预览体验；需先确认 ModManager 是否支持 reload。
- **写盘安全**：所有保存走「备份 + 临时文件 + 原子替换」，禁止直接覆盖。
- **范围蔓延**：三种模式全做会非常大，P0 只碰一条线，其余先留接口。

## 10. 补充：JVM 模组带来的变化（勘察 my-first-mod-1.0.0.jar 之后）

样例 jar 7.7MB，内容：`mod.toml`（id / entrypoint / name / version / minGameVersion）、
编译后的 Kotlin 类（含 `ComposableSingletons`、`HudSnapshot`）、`assets/`（mod-info.txt、build.json、music、maps、模板）。
mod-api 44 个 kt，模组可用的面：`game`（tick/调度/队伍/观察者）、`units`（DSL 造单位 + rawSection 逃生口）、
`unitWorld`、`commands`、`maps`、`rules`、`localization`、`audio`、`graphics`（含 `registerHud(id, order) { @Composable }`）、`ui`、`ai`。
**模组不再是纯数据，是可执行代码 + 资源 + 描述文件。**

### 10.1 模组两种形态（编辑器必须都认）

| 形态 | 工程内容 | 编辑器要做的 |
| --- | --- | --- |
| 数据模组 | `mods/units/<mod>/`：mod-info.txt、单位 ini、模板、贴图、音乐、地图 | ini 无损编辑、字段表单、模板展开、资源预览 |
| JVM 模组 | `mod.toml` + Kotlin/Java 源码 + gradle 工程 + 编译产物 jar + assets/ | 工程树、gradle 构建、API 补全、运行预览、HUD 预览、（可选）无代码生成代码 |

两者可以共存：JVM 模组照样带 `assets/mod-info.txt` 里的单位/地图/音乐段，
所以模组编辑模式要能「一个工程里既有 ini 又有代码」。

### 10.2 对编辑器底座的影响

- 工程模型要升级成 **Project**：不止一个目录，而是「描述文件 + 源集 + 资源集 + 构建脚本」。
- 需要构建集成：调用本机 gradle 编译模组（编辑器内嵌任务队列、输出到面板）。
- 需要运行/预览集成：起一局加载该模组，看单位、看 HUD 层（`registerHud` 支持多图层 order，可单独预览某一层）。
- 代码模组能执行任意逻辑 → 打开第三方模组工程时给出「会执行代码」的提示，预览运行前可要求确认。

### 10.3 打包模式的定义（老师这句是准绳）

> 打包模式就是把软件和模组合起来的模式。

所以打包模式的产物 = **客户端（引擎 jar / app-image / runtime）+ 选定模组（含 JVM jar 与 assets）+ 清单**，
要处理的事情：

1. 选择包含哪些模组、加载顺序、启用状态（写进整合包的 preferences/modSettings）。
2. 资源合并与冲突：同名文件、同 id 模组、同动画标签、同贴图路径 —— 冲突要报出来让人选。
3. **类冲突**：样例 jar 7.7MB，很可能自带了 Compose 运行时；多模组各带一份时靠 per-mod classLoader 隔离，
   但共享类型（mod-api、compose runtime）必须只有一份 —— 打包时要检测并裁剪重复依赖。
4. 清单与校验：文件清单、sha256、版本号、更新链接（样例 build.json 里就有 updateLink/updateType 字段）。
5. 产物可验证：解包后能跑、能加载每个模组、CHANGED-FILES 自动生成。

### 10.4 修订后的 P0（最小切片）

原 P0 只做 ini 一条线，现在加一条：**打开 JVM 模组工程（只读）**——工程树看到 `mod.toml`、源码、assets，
并能改 `mod.toml` 的 name/version/description 并存盘。不构建、不运行。
理由：编辑器要同时服务两种形态，先把「工程模型」这个底座验证掉，比先做深 ini 表单更值。

### 10.5 待老师定的新问题

1. JVM 模组工程的构建由 IDE 管（内置 gradle 任务）还是「只打开、构建走命令行」？
2. 打包时模组自带的 Compose/依赖怎么处理：强制剥离（用宿主的一份）还是允许带（隔离加载）？
3. 无代码路径：单位表单是生成 **DSL 代码** 还是生成 **rawSection ini**？（样例里 rawSection 与 DSL 并存）

## 11. 两种模式的技术差异（v2）

### 11.1 为什么必须分两种

- 模组符合游戏本体的契约：本体没开的接口，模组用不了。所以**模组编辑器只依赖契约，不依赖源码**。
  开发者拿官方正在更新的 RWX 正式版就能做模组，不需要 clone 引擎、不需要能编译整个游戏。
- 想改 UI、改接口设计、改模式设计的人，改的是本体本身。**客户端编辑器必须拿到源码树并能构建整包**。
  它的产物不是「装进游戏的东西」，而是「一个新的游戏」。

用一句话区分目标：

| | 模组编辑器 | 客户端编辑器 |
| --- | --- | --- |
| 目标 | 平台契约（API + ini 规范） | 引擎源码（core/desktop/ui/mod-api） |
| 需要源码吗 | 不需要 | 必须 |
| 构建什么 | mod jar | 整个客户端 app-image / 整合包 |
| 校验依据 | API 表面 + ini spec + minGameVersion | 编译通过 + 运行冒烟 |
| 预览 | 把模组挂到官方客户端跑一局 | 直接跑自己构建的客户端 |
| 产物 | 模组（可分发、可更新） | 软件（可分发、可更新） |
| 典型用户 | 内容作者、玩法作者 | 引擎/UI/模式开发者 |

### 11.2 模组产物结构（ini + Kotlin 合并进一个 jar，由代码调用启用）

```
my-mod.jar
├── mod.toml              # id / entrypoint / name / version / minGameVersion
├── com/example/...       # 编译后的 Kotlin/Java 类（entrypoint 指向这里）
└── assets/               # 数据侧：mod-info.txt、单位 ini、模板、贴图、音乐、地图
    ├── mod-info.txt
    ├── build.json
    └── units/ ...
```

要点：ini 模组和 Kotlin 模组**不是二选一**，而是同一个 jar 里的两侧。
数据侧照旧被引擎扫描；代码侧由 entrypoint 实例化后调用 init()，
代码可以选择「只用数据」「只写逻辑」「两者混用」。编辑器要为这两种写法都提供入口：
表单编辑 ini、代码编辑 Kotlin、以及二者之间的引用（代码里 `UnitId("ns:name")` 对应哪个 ini 单位）。

### 11.3 模组编辑器必须做「契约对齐」

- 本体是官方逐步更新的 RWX 正式版 → API 与 ini 规范会变。
- 编辑器要记录工程针对的平台版本（`minGameVersion`），并在打开时对照当前平台的 API/规范做漂移提示：
  用到了已移除的函数、ini 键拼错、字段在新版本改了含义。
- 校验规则来源：mod-api 的 DSL 表面 + ini spec 元数据（仓库里已有 `generateIniSpecMetadata` 任务）+ 现成的 lint 键表。

### 11.4 客户端编辑器要改的四类东西

1. **UI**：Compose 桌面层（desktop 模块）与局内 HUD（`graphics.registerHud` 那一层）。
2. **接口设计**：mod-api 表面本身 —— 新增能力会改变所有模组的可用范围，要带影响面提示。
3. **模式设计**：队伍/规则/胜负条件/开局流程（core 的 game mode 相关）。
4. **玩法**：直接改引擎行为，不再受契约约束。

### 11.5 打包（客户端编辑器的导出阶段）

- 输入：改过的源码 + 选定模组 + 资源 + runtime。
- 处理：构建、模组加载顺序与启用状态、资源冲突、类冲突（多模组各带 Compose 时的重复依赖裁剪）、清单与 sha256。
- 产物：可分发的客户端；解包后能跑、能加载每个模组、CHANGED-FILES 自动生成。

### 11.6 两个模式可共享的底座（复用清单）

工作区/任务队列、文档模型（文本为真源 + AST 索引）、撤销事务、校验器框架、诊断面板、资源预览。
不共享的是：构建管线、校验规则集、预览启动方式、导出产物格式。

### 11.7 这一版之后的新问题

1. 模组编辑器是否只面向官方 RWX 正式版？本仓库这个 fork（RWX-expand）自己要算另一种「平台」吗？
2. 客户端编辑器改 mod-api 表面时，是否需要「兼容性检查」阻止破坏性改动直接导出？
3. 一个工程能不能从「模组」升级成「客户端」？（含代码迁移与契约破坏提醒）

## 12. 客户端编辑器的工作面：基于 RWX 源码重构（实测数据）

老师的口径：客户端编辑器是基于 RWX 源码做重构，产物是一个改造过的新客户端。
所以它不是「配置编辑器」，而是一个**源码级重构工作站**。下面是实测的工作面规模。

| 模块 | Java | Kotlin | 代码行 | 说明 |
| --- | --- | --- | --- | --- |
| core | 710 | 221 | 195,590 | 引擎主体，**687 个文件带 JADX 反编译标记** |
| desktop | 37 | 42 | 14,135 | Compose 桌面壳 + Slick/Skia 渲染宿主 |
| ui | 0 | 40 | 4,807 | Compose UI |
| mod-api | 0 | 44 | 8,730 | 模组契约（44 个 kt） |
| slick2d-lwjgl3 | — | — | — | 渲染层移植 |
| mod-tools | — | — | — | 工具链 |
| bench-mod | 0 | 1 | 204 | 台架模组 |

巨型文件（重构时要特别小心）：
`OrderableUnit.java` 5,714 行、`NetworkEngine.java` 5,581 行、`CustomUnit.java` 5,000 行、`GameUI.java` 4,649 行。

### 12.1 重构能力分四级

| 级别 | 能力 | 说明 |
| --- | --- | --- |
| L0 | 浏览与索引 | 符号索引、定义/引用跳转、模块依赖图、调用链 |
| L1 | 安全重构 | 重命名、提取常量/方法、移动文件、格式化（不改行为） |
| L2 | 结构重构 | 拆模块、抽接口、加接缝（seam）；例如把 UI 从 core 剥离、把模式逻辑从 GameUI 抽出来 |
| L3 | 行为重写 | 改 UI 设计、改接口表面、改模式与玩法；然后构建导出新客户端 |

L1 是最该先做的：它能覆盖大量日常改动，行为风险最低；L2/L3 必须有构建 + 冒烟兜底。

### 12.2 反编译源码这条约束

core 里 687 个文件是 JADX 产物（`/* JADX INFO: renamed from: a */` 之类）。这意味着：
- 变量名、控制流、局部结构都不是原作者写的，**盲目「美化重构」会引入语序/副作用变化**；
- 安全策略：默认只做 L1（改名、提常量、抽方法且保持调用顺序），L2 起每次改动都要台架 A/B；
- 编辑器可以把「反编译痕迹」标注出来（哪些文件是 JADX 产物、哪些是本仓库手写的），提示风险等级。

### 12.3 必须的支撑设施

1. **符号索引**：710+221 个 Java/Kotlin 文件的类/方法/字段索引，支撑跳转与引用查找。
   （现有可用：javac 编译产物 + 自己扫，或接 Kotlin/Java 语言服务器；两条路都要量一次成本。）
2. **影响面分析**：改 mod-api 表面会波及哪些模组入口；改 GameUI 会影响哪些模式。
3. **构建反馈**：改 core 一次构建约 2 分钟 → 必须增量、后台、可取消，失败要定位到行。
4. **运行冒烟**：无头台架（1500 tick）+ GUI 冒烟（到主菜单）两条线，作为「重构没弄坏」的最低门槛。

### 12.4 风险

- **许可证**：RWX 引擎 AGPL-3.0，导出的客户端要跟着开源并保留声明；编辑器导出时要把许可证与声明文件带进产物。
- **mod-api 兼容**：客户端编辑器改了接口表面，老模组可能装不上 → 导出前做一次「模组兼容性检查」。
- **巨型文件**：5,000 行级别的单文件改动难以评审 → 优先「先抽接缝再加能力」，而不是就地魔改。
- **构建时间**：2 分钟/次的反馈回路，决定重构体验上限；必要时按模块拆构建。

### 12.5 客户端编辑器的分阶段

- S0：符号索引 + 浏览（模块图、定义/引用跳转、反编译痕迹标注）。
- S1：L1 安全重构 + 构建/冒烟一键跑。
- S2：L2 结构重构（先拿一个真实目标练手，例如 UI 从 core 剥离或 GameUI 拆分）。
- S3：L3 UI/接口/模式重写 + 导出新客户端（打包阶段）。

## 13. 骨架 v0（已落地，可编译可打开）

代码位置：独立 Gradle 模块 `:editor`（`editor/src/main/kotlin/io/github/rwx/editor/`）

| 文件 | 作用 | 状态 |
| --- | --- | --- |
| `Main.kt` | 独立程序入口（Compose `application { Window(...) }`） | 可用 |
| `EditorRoot.kt` | 左侧三个工作面切换（模组编辑 / 部件预览 / 客户端 UI） | 可用 |
| `ModEditorScreen.kt` | 扫 mods/units、列文件、截断读文本（4000 行上限） | 可读，不可写 |
| `PartPreviewScreen.kt` | 画布 + 网格 + 中心线 | 只有画布 |
| `ClientUiScreen.kt` | 只读展示全屏/垂直同步/渲染后端 | 只读 |

打开方式：`java -jar editor/build/compose/jars/RWX-Editor-windows-x64-0.1.0.jar [工作区目录]`，工作区也可用环境变量 `RWX_WORKSPACE` 指定；不传就自动找整合包或 RWPP 的 mods/units。

### 13.1 明确没做的（不假装）

- 无损文档模型：现在用 `readLines` 只读展示，**保存会丢注释**，所以没有保存入口。
- MCP 接入：右侧校验面板是占位文本，没有接 `rw-modding-mcp`。
- 预览器合流：画布画的是网格，没有解析 ini、不能拖拽、不写回。
- 客户端 UI 可改：只有只读数值，没有写回通道。

### 13.2 合流方案（下一步，按依赖排序）

1. **无损文档模型**：`Document`（行数组 + 行号→section/key 索引 + 脏标记），文本为真源。
   模组编辑的保存、预览器的拖拽写回都走它，保证只改目标行。
2. **预览器解析**：读 ini 里 base/turret/arm/leg 的坐标与贴图引用，画到画布（先只读，不写回）。
   预览器现有实现（RWPP 侧 `mods/预览器`：server.ps1/server.js + app.js）可以当规格参考，
   但它的写回逻辑要移植到 `Document` 上，不能直接复用文件级写。
3. **拖拽写回**：拖拽 = 一次文本区间替换（`x: 12` → `x: 18`），进撤销栈；保存前跑 lint。
4. **MCP 接入**：`rw-modding-mcp` 是 Python 只读工具（lint / lookup_key / get_ref / explain_actions / search_source）。
   接入方式二选一：进程内调用（把它的 Python 换成 HTTP/stdio 子进程）或由编辑器起一个本地 MCP 客户端。
   先接 `lint`（保存前必跑）与 `lookup_key`（键补全/纠错）。
5. **客户端 UI 可改**：把只读行换成「开关/滑杆 → 预览 → 写回 preferences.toml」，
   写回同样走 `Document` 保护注释。

### 13.3 骨架阶段的验证

- `:desktop:compileKotlin` 通过（scripts/build.sh，约 48 秒）。
- GUI 冒烟（实测）：单独起编辑器 jar，窗口列表只有 "RWX 编辑器（骨架）— <工作区>"，没有 "RWX Game"；无异常堆栈。

## 14. 编辑器是独立程序（v3 决定）

老师口径：编辑器本身是单独程序，不寄生在客户端进程里。已按此重构：

| 项 | 之前 | 现在 |
| --- | --- | --- |
| 代码位置 | desktop 模块内 `editor/` 包 | 独立模块 `:editor` |
| 启动方式 | 游戏启动后加 `-Drwx.editor=1` 附带开窗 | 独立 jar 直接启动，游戏不用起 |
| 依赖 | 跟着 desktop 一起吃 core / slick / lwjgl | 只依赖 Compose（`compose.desktop.currentOs` + material3） |
| 崩溃隔离 | 共用游戏进程 | 各自进程，互不影响 |
| 产物 | 无 | `RWX-Editor-windows-x64-0.1.0.jar`（后续可出 app-image） |

### 14.1 为什么这样更对

- 模组作者只做模组，不该为了改一个 ini 去起一个 2.7GB 的游戏进程。
- 编辑器崩溃不会带走游戏，游戏崩溃也不会带走未保存的编辑。
- 独立程序可以单独分发、单独版本号（现在 0.1.0）。
- 需要游戏能力时（局内预览、渲染校验）用**子进程或本地服务**去接，比如起 headless 会话或调用 RWPP 的预览器服务，
  而不是把编辑器塞进引擎进程。

### 14.2 独立化之后的接口变化

- 不能直接引用 `SettingsEngine` 之类引擎类了：客户端 UI 面板改成直接读 `preferences.toml` 文本。
  这也正好逼着我们把「配置读写」做成编辑器自己的文档模型，而不是借引擎的内存对象。
- 工作区从命令行参数或 `RWX_WORKSPACE` 传入，默认自动探测整合包 / RWPP 的 `mods/units`。

### 14.3 验证（实测）

- `:editor:packageUberJarForCurrentOS` 通过，产物 `editor/build/compose/jars/RWX-Editor-windows-x64-0.1.0.jar`。
- 直接 `java -jar` 启动：窗口标题为「RWX 编辑器（骨架）— D:/Game/RWX-整合包/mods/units」，
  窗口列表中没有 "RWX Game"，即确实没起游戏。
